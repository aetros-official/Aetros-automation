```
┌──────────────────────┐
│  Enterprise Travel   │
│     Portal UI         │

└─────────────▲────────┘
              │
              │ REST / SOAP
              │
┌─────────────▼────────┐
│  API Gateway Layer   │
│  (Rate‑Limiting, CORS)│
└─────────────▲────────┘
              │
              │
┌───────▼───────┐
│  GDS / CRS     │
│  (Amadeus /    │

```

* **Front‑end**: Widgets are embedded within your custom branding; they pull data via the API Gateway.  
* **Back‑end**: The API Gateway routes requests to the respective GDS/CRS services, caches results (where appropriate), and formats them for UI consumption.  
* **No affiliate**: All booking funnels terminate directly in the carrier or hotel CRS, guaranteeing 100% revenue capture and compliance.

## 2. Flight Search – Direct Airline Schedules

### 2.1 API Endpoint & Query Parameters

| Parameter | Type | Description | Example |
|-----------|------|-------------|---------|
| `origin` | string | 3‑letter IATA code | `IST` |
| `destination` | string | 3‑letter IATA code | `NYC` |
| `departure_date` | string | YYYY‑MM‑DD | `2026-12-01` |
| `return_date` | string (optional) | YYYY‑MM‑DD | `2026-12-10` |
| `cabin` | string | `ECONOMY`, `BUSINESS`, `FIRST` | `BUSINESS` |
| `passengers` | integer | Number of passengers (adults only) | `1` |
| `include_cabin_availability` | boolean | Request live seat availability | `true` |
| `currency` | string | ISO 4217 | `USD` |

> **Endpoint**  
> `POST https://api.enterprise-portal.com/v1/flights/search`

> **Headers**  
> ```
> Authorization: Bearer <GDS-API-Key>
> Content-Type: application/json
> ```

### 2.3 Live Cabin Class Availability

* `availability.seats_remaining` is **real‑time**; query the API every 5 s during the booking window to keep seat counts accurate.  
* When `seat_map_available` is `true`, expose seat‑by‑seat selection on the widget.

### 2.4 Seat & Fare Validation

1. **Pre‑Booking Validation**:  
   * Call `POST /v1/flights/validate` with selected flight ID and seat count.  
   * Response: `{"valid": true, "new_total": 1000.00}`

2. **Lock‑in**:  
   * `POST /v1/flights/lock` with `search_id` and `selected_flight_id`.  
   * GDS reserves a *ticket‑generation window* (usually 30 min).  
   * Receipt: `ticket_token` for final booking.

* `cancellable_until` indicates the last moment a free cancellation can be requested.

## 5. Booking Workflow

| Step | API Call | Description |
|------|----------|-------------|
| 1 | **Flight Search** (`/v1/flights/search`) | Retrieve live schedules and availability. |
| 2 | **Flight Validation** (`/v1/flights/validate`) | Ensure seat count and fare are still valid. |
| 3 | **Flight Lock** (`/v1/flights/lock`) | Reserve the ticket for 30 min. |
| 4 | **Hotel Search** (`/v1/hotels/search`) | Retrieve room inventory and rates. |
| 5 | **Hotel Booking** (`/v1/hotels/book`) | POST `{search_id, rate_plan_id, guests}` → CRS. |
| 6 | **Final Booking** (`/v1/flights/book`) | POST `{ticket_token, passenger_details}` → GDS. |
| 7 | **Payment Capture** | Use your payment gateway; embed a token returned from `/v1/payments/create`. |
| 8 | **Confirmation** | GDS/CRS return `pnr`, `confirmation_number`, and QR codes. |

## 6. Error Handling & Fallback Strategy

| Error Code | Message | Suggested Action |
|------------|---------|-------------------|
| `400` | Bad Request | Validate payload; ensure required fields are present. |
| `401` | Unauthorized | Refresh OAuth token; check API key. |
| `429` | Too Many Requests | Implement exponential back‑off; queue request. |
| `503` | Service Unavailable | Retry after 30 s; inform user of temporary outage. |
| `GDS-ERR-001` | Seat count changed | Re‑validate; ask user to select new seat. |
| `CRS-ERR-002` | Room not available | Offer alternate dates or properties. |

> **Graceful Degradation**  
> • If the widget fails to load, display a fallback message: “We’re experiencing a connectivity issue. Please try again later.”  
> • Store search parameters client‑side and retry automatically after a short delay.

## 7. Performance & Rate‑Limit Optimizations

* **Caching Layer**  
  * **Flight schedules**: Cache for 1 h (static); update every 10 min.  
  * **Hotel rates**: Cache for 5 min; refresh on every lock‑in request.  

* **Batch Requests**  
  * Combine multiple flight searches into a single POST to `/v1/flights/search/batch`.  
  * Similarly, batch hotel searches for large cities.

* **WebSocket Push**  
  * For high‑traffic portals, implement a WebSocket endpoint `wss://api.enterprise-portal.com/realtime` to push live inventory updates without polling.

## 8. Security & Compliance

* **OAuth 2.0** – All API calls require a bearer token. Tokens expire after 15 min; use refresh endpoint `/v1/auth/refresh`.  
* **TLS 1.3** – All data in transit is encrypted.  
* **PCI‑DSS** – Payment processing is handled by a compliant third‑party; no card data ever touches the portal.  
* **GDPR** – Customer data is stored only in the CRS/Flight PNR; the portal does not keep personal data beyond the booking window.

## 9. FAQ & Troubleshooting

| Topic | Question | Answer |
|-------|----------|--------|
| Widget | Why does the seat map not show? | The carrier’s seat map service is temporarily unavailable; fallback to list view. |
| Booking | My PNR shows as `N` (No Show) after cancellation | Contact the carrier directly; the CRS may require a separate cancellation request. |
| Rates | Are the rates inclusive of all taxes? | Yes – see `breakdown.taxes` and `breakdown.fees` in the hotel response. |
