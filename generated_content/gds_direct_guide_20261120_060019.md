## 1. Introduction  

This guide provides a **white‑label, zero‑affiliate** blueprint to embed live, authoritative GDS/CRS data into an enterprise travel portal. Leveraging the **Amadeus/Sabre Core Engine**, you gain real‑time flight schedules, cabin class availability, and hotel rates for *IST* (Istanbul). The focus is on:

- **High‑fidelity integration**: Pull data directly from the GDS/CRS, not through third‑party APIs.  
- **Conversion‑centric UI**: Widgets that reduce friction and build trust by showing “live” availability.  
- **Technical rigor**: Detailed API flow, payload schemas, and rate‑management strategies.

## 6. Integration Blueprint  

### 6.1. Flight Search Widget – `[GDS_FLIGHT_SEARCH_WIDGET]`

1. **User Flow**  
   - Enter origin/destination, dates, passengers, cabin preference.  
   - Widget calls the `flights/search` endpoint.  
   - Results are rendered in a responsive table.  
   - Clicking a flight triggers the **booking** modal that loads seat inventory.

2. **Technical Stack**  
   - **Frontend**: React (or Vue) – custom component `<GDSFlightSearchWidget/>`.  
   - **Backend**: Node.js/Java (or Python) micro‑service exposing `/internal/flights/search`.  
   - **Security**: OAuth 2.0 token from Amadeus/Sabre.  
   - **Caching**: In‑memory TTL 30 s for identical queries.

3. **Key API Call**  
   ```http
   POST /internal/flights/search
   Content-Type: application/json
   Authorization: Bearer {amadeus_token}
   ```
   ```json
   {
     "origin": "IST",
     "destination": "LHR",
     "departureDate": "2026-12-20",
     "returnDate": "2026-12-27",
     "adults": 2,
     "cabinClass": "ECONOMY"
   }
   ```

4. **Response Handling**  
   - Parse `pricingInfo` and display **price per seat**.  
   - Highlight `cabinClass` options with real‑time seat count.  
   - Use **client‑side time‑zone conversion** via Intl.DateTimeFormat.

5. **Booking Flow**  
   - On selection, call `/flights/availability` to lock seats.  
   - Create a **PCC‑based** booking record in your CRS.  
   - Return a secure **confirmation number** and booking URL.

### 6.2. Hotel Inventory Widget – `[CRS_HOTEL_INVENTORY_WIDGET]`

1. **User Flow**  
   - Input city (`IST`) and dates.  
   - Widget requests `/hotels/inventory`.  
   - Render property cards with *rate, rating, and availability* badges.  

2. **Technical Stack**  
   - **Frontend**: Angular or Svelte – `<CrHotelInventory/>`.  
   - **Backend**: Go or Ruby on Rails micro‑service `/internal/hotels/inventory`.  
   - **Security**: OAuth 2.0 token to CRS.  
   - **Caching**: 1‑minute TTL for each city/date combo.

3. **Key API Call**  
   ```http
   POST /internal/hotels/inventory
   Authorization: Bearer {crs_token}
   ```
   ```json
   {
     "cityCode": "IST",
     "checkInDate": "2026-12-20",
     "checkOutDate": "2026-12-27",
     "rooms": 1,
     "adultsPerRoom": 2,
     "childrenPerRoom": 0
   }
   ```

4. **Response Handling**  
   - Map `hotelId` to your internal property catalog.  
   - Show **price per night**, total nights, and *guaranteed* flag.  
   - If `rooms[].available === false`, grey‑out the booking button.

5. **Booking Flow**  
   - On click, call `/hotels/booking` with the chosen `roomType`.  
   - Store the **booking reference** and expose to the user.

## 8. Conversion‑Optimised UX Patterns  

| Pattern | Why It Works | Implementation |
|---------|--------------|----------------|
| **Live Seat Countdown** | Builds urgency | `setInterval` to update seat count every 30 s |
| **Price‑to‑Person Breakdown** | Transparency | Show per‑seat price + taxes before checkout |
| **Instant Availability Badges** | Trust | “Available in 3 seats” or “Fully booked” |
| **Responsive Date Picker** | Mobile friendliness | Use flatpickr or similar, disable past dates |
| **One‑Click Booking** | Reduce friction | Auto‑fill passenger details from profile |
| **Real‑Time Error Handling** | Avoid drop‑off | Show API‑level errors (e.g., “No seats left”) instantly |

> **Performance**: Ensure widget loads in < 200 ms by using **edge caching** for static assets and **streaming** the API responses.

## 9. Compliance & Data Governance  

| Aspect | Requirement | Implementation |
|--------|-------------|----------------|
| **GDPR** | Collect minimal personal data, obtain consent | Consent banner before booking |
| **PCI‑DSS** | Secure payment integration | Use tokenization; never store card details |
| **CORS** | Cross‑origin security | Set `Access-Control-Allow-Origin: https://yourdomain.com` |
| **Rate Limits** | Respect GDS/CRS limits | Implement back‑off & retry logic with exponential back‑off |
| **Audit Logs** | Traceability | Store each booking request with timestamp, user IP, and GDS response |

> **Note**: The widgets should embed **direct GDS/CRS URLs** for the final booking confirmation page, not redirect through affiliates.
