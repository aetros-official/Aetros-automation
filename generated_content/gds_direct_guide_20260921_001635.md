## 1️⃣ Overview of Direct GDS/CRS Architecture  

| Component | Description | Primary Protocol |
|-----------|-------------|------------------|
| **GDS Core Engine** | Direct connection to Amadeus & Sabre (NDC/OTA) for airline schedules, seat maps, fare families, ancillary pricing. | **NDC XML/JSON**, **OTA Air** |
| **CRS Hotel Engine** | Real‑time access to property inventory, rate plans, and restriction rules (e.g., GDS‑Hotel, Pegasus, Sabre SynXis). | **OTA Hotel**, **JSON‑API** |
| **Enterprise Middleware** | Normalises heterogeneous payloads into a canonical **Travel‑Data Model (TDM)**. Handles transformation, enrichment, and business rules. | **REST/GraphQL**, **Kafka** (for streaming updates) |
| **Booking Orchestration Service** | Executes atomic multi‑leg bookings, applies fare‑construction logic, and writes confirmed PNRs to the GDS/CRS. | **SAGA pattern**, **Two‑Phase Commit** |
| **Analytics & Reporting Engine** | Real‑time dashboards for conversion, fare elasticity, and inventory utilisation. | **ElasticSearch + Kibana** |
| **Compliance Layer** | GDPR/PCI‑DSS tokenisation, audit logs, and consent management. | **Vault**, **AuditDB** |

> **Key Principle:** 0 % reliance on external affiliate APIs – every data point originates from the *direct* GDS (Amadeus/Sabre) or the *central* CRS for hotels.

## 2️⃣ Real‑Time Airline Schedule Retrieval  

### 2.1 Query Construction (NDC)  

```xml
<AirShoppingRQ Version="19.0" xmlns="http://www.iata.org/IATA/2015/00/01/Amadeus/">
  <Party>
    <Sender>
      <TravelAgencySender>
        <AgencyID>YOUR_AGENCY_ID</AgencyID>
        <IATA_Number>YOUR_IATA_NUM</IATA_Number>
      </TravelAgencySender>
    </Sender>
  </Party>
  <Document>
    <Reference>IST‑SEARCH‑{{timestamp}}</Reference>
  </Document>
  <CoreQuery>
    <OriginDestinations>
      <OriginDestination>
        <Departure>
          <AirportCode>IST</AirportCode>
          <Date>2026-10-15</Date>
        </Departure>
        <Arrival>
          <AirportCode>LHR</AirportCode>
        </Arrival>
      </OriginDestination>
    </OriginDestinations>
    <CabinPreferences>
      <CabinClass>Economy</CabinClass>
      <CabinClass>Business</CabinClass>
      <CabinClass>First</CabinClass>
    </CabinPreferences>
  </CoreQuery>
</AirShoppingRQ>
```

*Result:* A **FlightOffer** list with **Carrier**, **FlightNumber**, **Departure/Arrival timestamps**, **Aircraft**, and **Seat‑Map URL**.  

### 2.2 Direct Seat‑Map Extraction  

- **GET** `/seatmap/v1/{carrier}/{flightNumber}/{date}` → Returns a **binary PNG** and a **JSON** with seat‑class availability counts (e.g., `{"Y":12,"J":4,"F":2}`).  

### 2.3 Integration Hook  

```markdown
[ GDS_FLIGHT_SEARCH_WIDGET ]
```

*The widget consumes the JSON payload above, renders an interactive schedule grid, and allows **instant seat‑class selection** without any third‑party redirects.*

### 3.2 Real‑Time Availability Algorithm  

```pseudo
for each FlightOffer in GDSResponse:
    seatMap = GET SeatMap(FightOffer.id)
    availability = {
        Y: seatMap.count('Y'),
        J: seatMap.count('J'),
        F: seatMap.count('F')
    }
    fareList = BuildFareMatrix(availability, PricingRules)
    attach fareList to FlightOffer
return enriched FlightOffer list
```

## 5️⃣ White‑Label Booking UI Integration  

### 5.1 UI Component Map  

| Widget Placeholder | Rendered Component | Data Source | Primary Actions |
|--------------------|--------------------|-------------|-----------------|
| `[GDS_FLIGHT_SEARCH_WIDGET]` | Interactive flight grid, seat‑map overlay, fare‑family selector. | Amadeus/Sabre NDC & Seat‑Map APIs | **Select → Add to Cart** |
| `[CRS_HOTEL_INVENTORY_WIDGET]` | Hotel carousel, rate‑plan matrix, real‑time room count. | CRS OTA Hotel API | **Select → Reserve** |

### 5.2 Integration Flow  

1. **User initiates search** → Front‑end calls `/api/v1/search/flight?origin=IST&dest=LHR&date=2026-10-15`.  
2. Middleware queries **NDC** → Returns enriched flight offers.  
3. UI renders `[GDS_FLIGHT_SEARCH_WIDGET]`.  
4. User selects cabin/fare → Booking Orchestrator creates a **PNR** via **NDC AirBooking**.  
5. Parallel hotel search → `/api/v1/search/hotel?city=IST&checkin=2026-10-15&checkout=2026-10-20`.  
6. CRS response feeds `[CRS_HOTEL_INVENTORY_WIDGET]`.  
7. Final **bundle** (flight + hotel) → Single transaction commit to both GDS (PNR) and CRS (Reservation).  

> **No Affiliate Calls** – all endpoints are owned by your enterprise stack.

## 6️⃣ Data Normalisation & Mapping Layer  

| GDS/CRS Field | Canonical TDM Field | Transformation |
|---------------|---------------------|----------------|
| `FlightNumber` | `flight.id` | `CarrierCode + FlightNumber + Date` |
| `DepartureDateTime` | `flight.departure` | ISO‑8601 with timezone |
| `ArrivalDateTime` | `flight.arrival` | ISO‑8601 with timezone |
| `CabinClass` | `flight.cabin` | Map `Y`→`Economy`, `J`→`Business`, `F`→`First` |
| `SeatAvailability` | `flight.seatCount` | Summarise per cabin |
| `HotelCode` | `hotel.id` | Direct mapping from CRS |
| `RatePlanID` | `hotel.ratePlan.id` | Preserve original ID for amendment |
| `BaseRate` | `hotel.ratePlan.basePrice` | Convert to portal base currency (USD) using live FX feed |

The **Mapping Service** is a stateless microservice exposing a `/transform` endpoint; all downstream services consume its output to guarantee schema consistency.

## 7️⃣ Performance, Caching & Rate‑Limiting  

| Layer | Strategy | TTL / Limits |
|-------|----------|--------------|
| **Flight Schedule** | **In‑memory LRU cache** keyed by `origin|dest|date`. | 5 minutes (GDS updates every 2 min). |
| **Seat‑Map** | **Redis hash** per `flightId`. | 1 minute (seat changes are high‑frequency). |
| **Hotel Rates** | **Write‑through cache** with **ETag** validation. | 2 minutes. |
| **API Gateway** | **Token bucket** per client IP (100 req/s). | Auto‑scale burst up to 200 req/s. |
| **Back‑pressure** | **Circuit Breaker** on GDS/CRS latency > 3 s. | Fallback to *last‑known* snapshot with stale‑data disclaimer. |

Monitoring dashboards display **latency heat‑maps**, **cache hit ratios**, and **error‑rate trends** in real time.

## 8️⃣ Security, Compliance & Auditing  

| Requirement | Implementation |
|-------------|----------------|
| **PCI‑DSS** | All payment data tokenised via **PCI‑validated vault**; never stored in plain text. |
| **GDPR** | Personal identifiers hashed; consent flag stored per booking; right‑to‑erasure endpoint `/api/v1/users/{id}/purge`. |
| **Transport Security** | Mutual TLS (mTLS) between portal and GDS/CRS endpoints. |
| **Audit Trail** | Immutable **append‑only log** in **Cassandra** capturing request/response hashes, timestamps, and user IDs. |
| **Role‑Based Access Control (RBAC)** | Granular scopes (`flight:read`, `hotel:write`, `booking:execute`). |

All logs are **anonymised** before ingestion into analytics to preserve privacy.
