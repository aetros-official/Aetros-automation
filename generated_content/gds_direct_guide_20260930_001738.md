> 1️⃣ **Accuracy** – data is live, eliminating the lag of feed‑based systems.  
> 2️⃣ **Control** – full ownership of pricing, inventory & booking flow, enabling dynamic pricing & upsell opportunities.  
> 3️⃣ **Compliance** – GDPR, CCPA, PCI‑DSS compliant from the ground up.

## 3. Flight Search & Booking Flow  

### 3.1 API Design (Amadeus / Sabre)  

| Endpoint | Purpose | Key Parameters | Sample Response |
|----------|---------|----------------|-----------------|
| `GET /v1/flight/availability` | Search flights by route & date | `origin`, `dest`, `date`, `cabin`, `passengers` | `[{ "flightNumber": "AZ123", "carrier": "Aegean", ... }]` |
| `POST /v1/booking/flight` | Create a reservation | `flightId`, `passengerDetails`, `paymentInfo` | `{"bookingReference": "ABC123", "status": "Confirmed"}` |

> **Best practice:** Use **bulk queries** (e.g., `flightNumber, cabin, date`) to reduce round‑trips.

### 3.2 Widget Integration  

Insert the following snippet into your front‑end (e.g., React component) to provide a **direct seat booking** UI:

```markdown
[GDS_FLIGHT_SEARCH_WIDGET]
```

The widget automatically:

1. Queries live schedules & cabin availability.  
2. Presents a filterable list by cabin, price, layover time, etc.  
3. Allows instant seat selection & booking via a secure, PCI‑DSS compliant checkout.

> **Conversion Tip:**  
> Add a “Dynamic Pricing Alert” – notify users when a fare drops < 5 % in the next 60 minutes.

## 5. Technical Implementation Blueprint  

### 5.1 Authentication & Security  

| Layer | Method | Notes |
|-------|--------|-------|
| **GDS/CRS Auth** | OAuth 2.0 Client Credentials | Use a dedicated service account. Rotate tokens every 10 min. |
| **API Gateway** | TLS‑1.3, IP Whitelisting | Protect against SSRF, use WAF. |
| **Data at Rest** | AES‑256 | Store cache keys only; never persist raw rate data. |
| **PCI‑DSS** | Tokenization & 3D‑Secure | Payment data never touches your servers. |

### 5.2 Caching Strategy  

| Resource | Cache TTL | Cache Invalidation | Notes |
|----------|-----------|--------------------|-------|
| Flight Availability | 5 s | On each `GET` | Must be live for seat accuracy. |
| Hotel Rates | 5 s | On each `GET` | Avoid over‑caching to respect price changes. |
| Static Metadata (Carriers, Airports) | 24 h | Daily refresh | Good for lookup tables. |

### 5.3 Error Handling & Retries  

- **Transient errors**: HTTP 429/500 – exponential back‑off up to 3 retries.  
- **Rate limits**: Respect `X‑RateLimit-Reset` header.  
- **Missing data**: Fallback to *no result* UI, not cached.

### 5.4 Logging & Analytics  

| Metric | Source | Tool | Action |
|--------|--------|------|--------|
| API latency | `X‑Request‑Duration` | Prometheus | Alert if > 200 ms |
| Conversion rate | Booking endpoint | Mixpanel | Optimize UI |
| Seat fill | Flight response | SQL | Dynamic pricing model |

## 10. FAQ

| Question | Answer |
|----------|--------|
| **Do I need a GDS/CRS account?** | Yes, a direct API key is mandatory. |
| **How do I handle fare restrictions?** | Retrieve `FareRule` via `/fare_rules/{fareBasis}`; display in modal. |
| **Can I use dynamic pricing?** | Yes, but must reflect live rates; avoid over‑promising. |
| **What if a flight is over‑booked?** | The widget will display “Full” status; provide alternative dates. |
| **Can I bundle flights and hotels?** | Use the `/bundle` endpoint if available; otherwise offer a cross‑sell UI. |

| Term | Definition |
|------|------------|
