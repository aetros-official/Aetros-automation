# Travel & Fare Analysis Guide  
*Enterprise White‑Label Booking Platform – Direct GDS/CRS Integration*  

> **Audience:** Integration Engineers, Product Managers, Data Scientists  
> **Scope:** End‑to‑end flight and hotel data ingestion from Amadeus/Sabre GDS and live CRS feeds for Istanbul (IST).  
> **Version:** 1.0 – 2026‑10‑02  

---

## 1. Executive Summary

This guide documents the technical framework for consuming **direct** airline schedules, cabin‑class availability, and hotel inventory from Amadeus/Sabre GDS and CRS. The objective is to expose this data to a white‑label portal via two plug‑in widgets – one for flights, one for hotels – while eliminating any dependence on affiliate networks. All booking decisions, pricing, and seat inventory are sourced **directly** from the GDS/CRS engines, ensuring compliance, price parity, and real‑time accuracy.

## 2. Architecture Overview

```
┌───────────────────────┐      REST/JSON     ┌───────────────────────┐
│  White‑Label Frontend  │◄──────────────────►│  GDS/CRS API Layer     │
└───────────────────────┘  (SOAP, REST)     └───────────────────────┘
          ▲                               ▲
          │                               │
          │  [GDS_FLIGHT_SEARCH_WIDGET]  │
          │  [CRS_HOTEL_INVENTORY_WIDGET]│
          │                               │
┌───────────────────────┐      Streaming      ┌───────────────────────┐
│   Real‑Time Data Store │◄──────────────────►│  Data Lake / Cache    │
└───────────────────────┘     (Kafka/Redis)  └───────────────────────┘
```

1. **GDS/CRS API Layer**  
   - **Amadeus/ Sabre Core Engine** (flight)  
   - **Amadeus/ Sabre CRS** (hotel)  
   All calls are authenticated via **OAuth 2.0** or **SAML** per GDS vendor.

2. **Data Lake / Cache**  
   - Stores parsed flight/hotel objects, pricing, and inventory snapshots.  
   - Provides *near real‑time* query acceleration for the widgets.

3. **Widgets**  
   - `[GDS_FLIGHT_SEARCH_WIDGET]`: A fully styled, white‑label iframe or component that performs *instant* booking by sending the user’s search parameters back to the GDS API.  
   - `[CRS_HOTEL_INVENTORY_WIDGET]`: Same concept for hotel search and reservation.

## 3. Direct Airline Schedules

| Element | Description | API Endpoint (Example) | Data Fields |
|---------|-------------|------------------------|-------------|

| **Aircraft Type** | e.g., `A320` | `aircraft_type` |  |
| **Direct/Connecting** | Flag | `direct_flight` | `true/false` |
| **Schedule Frequency** | Daily/Weekly pattern | `schedule_pattern` |  |

> **Implementation Tip:** Use **Amadeus Flight Offers Search** (`/v1/reference-data/airlines`) for static data and **Amadeus Availability** (`/v1/booking/availability`) for real‑time seat availability.

## 6. White‑Label Integration Widgets

### 6.1. `[GDS_FLIGHT_SEARCH_WIDGET]`

```html
<div id="flight-search-widget"></div>

<script>
  initFlightSearchWidget({
    container: '#flight-search-widget',
    gdsEndpoint: 'https://gds.example.com/v1/flight/search',
    oauthToken: '{{YOUR_GDS_OAUTH_TOKEN}}',
    locale: 'en-US',
    defaultSearch: {
      origin: 'IST',
      destination: 'LHR',
      departureDate: '2026-10-15',
      cabin: 'Y'
    },
    callbacks: {
      onSearch: (query) => { /* log analytics */ },
      onSelect: (offer) => { /* proceed to booking flow */ }
    }
  });
</script>
```

- **Parameters** – `origin`, `destination`, `departureDate`, `cabin`, `adults`, `children`, `infants`.  
- **Output** – Flight offers with seat availability, fare, and pricing breakdown.  
- **Booking Flow** – When a user selects an offer, the widget posts a `POST /booking` request directly to the GDS with the selected `flight_key` and passenger data.

### 6.2. `[CRS_HOTEL_INVENTORY_WIDGET]`

```html
<div id="hotel-search-widget"></div>

<script>
  initHotelSearchWidget({
    container: '#hotel-search-widget',
    crsEndpoint: 'https://crs.example.com/hotel/v3/property',
    oauthToken: '{{YOUR_CRS_OAUTH_TOKEN}}',
    locale: 'en-US',
    defaultSearch: {
      city: 'Istanbul',
      checkIn: '2026-10-15',
      checkOut: '2026-10-20',
      rooms: 1
    },
    callbacks: {
      onSearch: (query) => { /* analytics */ },
      onSelect: (room) => { /* proceed to booking */ }
    }
  });
</script>
```

- **Parameters** – `city`, `checkIn`, `checkOut`, `rooms`, `guests`.  
- **Output** – Room availability, rate, taxes, and property details.  
- **Booking Flow** – The widget posts to `POST /booking` on the CRS, passing `property_id`, `room_type`, dates, and guest info.

## 8. Pricing & Tax Calculation

1. **Base Fare** – From GDS/CRS.  
2. **Taxes & Fees** – Structured per `taxes` array in API response.  
3. **Currency Conversion** – If the user’s locale differs from the base currency, use the **Real‑Time FX** endpoint (`/v1/reference-data/financial/currency-conversion`).  
4. **Total** – Sum base + taxes + fees.  

```js
function calculateTotal(offer) {
  const base = parseFloat(offer.price.amount);
  const taxes = offer.taxes.reduce((sum, t) => sum + parseFloat(t.amount), 0);
  return base + taxes;
}
```

## 9. Performance & Scalability

| Component | Recommendation | Rationale |
|-----------|----------------|-----------|
| **Caching** | Redis cache with TTL = 30‑60 sec for flight availability; 5‑10 min for hotel rates | Avoids repeated GDS calls while preserving real‑time accuracy |
| **Batching** | Use Amadeus “Bulk Availability” endpoint where possible | Reduces round‑trips for multi‑city searches |
| **Rate Limiting** | Implement back‑off logic; GDS caps: 5,000 req/min | Prevents API throttling |
| **Observability** | Instrument with OpenTelemetry | Trace request/response latency |

## 10. Security & Compliance

- **Authentication** – OAuth 2.0 with client credentials; rotate secrets monthly.  
- **Encryption** – TLS 1.3 for all network traffic.  
- **Data Residency** – Keep all booking data within the host country’s jurisdiction unless explicitly permitted.  
- **Audit Logs** – Record each `GET`/`POST` call with timestamp, user ID, and payload.
